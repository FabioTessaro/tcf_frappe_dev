# 108 · Portal internationalisation

## Purpose

Portal strings, where they live and how they merge. Server-side and Desk strings are governed by
[20-backend/205-i18n-server](../20-backend/205-i18n-server.md).

## Locations

| Location | Holds | Owner |
|---|---|---|
| `shared/i18n/locales/` | Common strings: generic buttons, statuses, validation, date and number labels | Core |
| `platform/<feature>/locales/` | Core features (login, launcher) | Core |
| `<feature-app>/frontend/locales/` | App-wide strings: app name, navigation | Feature app |
| `<feature-app>/frontend/features/<feature>/locales/` | One feature | Feature app |
| `errors.*` namespace (generated) | Error code messages | Generated from the error catalog |

`shared/i18n/` also holds `merge-locales.ts`, `languages.ts`, `apply-language.ts` (each with a
test) and `index.ts`.

## Rules

- `FE-I18N-001` The portal MUST use its **own keys**; it MUST NOT display Desk doctype or field
  labels, so portal copy can differ from Desk.
- `FE-I18N-002` Keys MUST be namespaced by app and feature so merging cannot collide.
- `FE-I18N-003` Resolution order: feature → app → core common → default language.
- `FE-I18N-004` Every location MUST provide one file per supported language with exactly the same
  keys as the default language.
- `FE-I18N-005` Shared components take default texts from core common strings and accept
  overrides through props or slots; they ship no locale files of their own.
- `FE-I18N-006` Error messages MUST be looked up by error code in the generated `errors.*`
  namespace, never hand-written per feature.
- `FE-I18N-007` Translators work in the self-hosted translation tool (Weblate) on these JSON files
  ([50-delivery/504-toolchain](../50-delivery/504-toolchain.md)).

## Verification

`locales-parity` contract test (FE-I18N-002, 004); generated-artifacts check (FE-I18N-006).
