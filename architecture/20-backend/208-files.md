# 208 · Files

## Purpose

One file pipeline for every entry point (portal uploads, document discussions, chat, email
attachments, job applications, personal drive, PLM/CAD/FE data), storing everything in an
S3-compatible object store (reference: SeaweedFS).

## Architecture

1. **Storage backend (core).** Core implements Frappe's `write_file` and
   `delete_file_data_content` hooks against the object store, and a **download route** that checks
   permission, classification and scan status, audits the access, then redirects to a short-lived
   presigned URL or streams the file. Every `File` doc — including those Frappe creates itself
   (email attachments, Desk uploads) — is stored in the object store.
2. **Storage classes.** Features name a class; configuration maps classes to buckets.

   | Class | Default bucket (reference deployment) | Use |
   |---|---|---|
   | `attachments` | `attachments-vault` | Document attachments, discussions, email |
   | `drive` | `drive-vault` | Personal and shared drive |
   | `engineering` | `cad-vault` | PLM: CAD, FE data |
   | `public` | `public-assets` | Deliberately public content |
   | `quarantine` | `quarantine` | Uploads awaiting antivirus scan |
   | `audit-archive` | `audit-archive` | Append-only audit export ([30-security-and-compliance/302-audit](../30-security-and-compliance/302-audit.md)) |

3. **File policies.** Each feature declares policies in `files.py`.

   | Policy field | Meaning |
   |---|---|
   | `storage_class` | Target class |
   | `allowed_types` | MIME types, checked by content (magic bytes), not extension |
   | `max_size` | Bytes; the site-wide `max_file_size` remains a ceiling |
   | `antivirus` | `off` · `async` (quarantine, then release) · `required` (no access until clean) |
   | `previews` | Thumbnail/preview generation on or off |
   | `classification` | Default classification of stored files |
   | `retention_class` | Records-management retention |
   | `immutable_after` | Optional state after which bytes can never change (e.g. PLM release) |
   | `direct_transfer` | Use presigned multipart transfers (large files) |

4. **Antivirus flow.** Upload → `quarantine` → scan job via the `virus_scanner` capability
   (reference: ClamAV container) → move to target class, `scan_status=clean`; infected files stay
   quarantined, flagged and audited.
5. **Large files.** Core issues presigned multipart upload URLs after a permission check; the
   client uploads directly to the object store; a "complete" call registers the File, verifies size
   and SHA-256, and triggers scanning and previews. Downloads use presigned URLs the same way.

## Rules

- `BE-FILE-001` Files MUST NOT be stored on the local filesystem in any non-development
  environment.
- `BE-FILE-002` Files MUST be private by default; public storage only for deliberately public
  content through the `public` class.
- `BE-FILE-003` Object keys MUST be `<storage-class>/<app>/<feature>/<uuid>`; user-supplied file
  names are metadata only.
- `BE-FILE-004` Every upload MUST be attached to a document and field; an orphan-cleanup job
  deletes unattached files after 24 h.
- `BE-FILE-005` Every feature that stores files MUST declare a policy; the portal uploads through
  feature endpoints applying that policy, not Frappe's generic `upload_file`.
- `BE-FILE-006` Policy defaults are code; administrators MAY tighten them in settings but MUST NOT
  loosen them below the code default.
- `BE-FILE-007` Files from external sources (Website Users, email, job applications, integration
  API) MUST use `antivirus: required` unless an ADR justifies otherwise.
- `BE-FILE-008` The download route MUST refuse files whose scan status is not `clean` when the
  policy requires a scan, and MUST audit reads when the file's classification requires it.
- `BE-FILE-009` Every stored object MUST have its SHA-256 recorded; immutable objects MUST be
  verified on read for controlled classifications.
- `BE-FILE-010` Previews and thumbnails MUST be generated by jobs and inherit the original's
  classification and permissions.
- `BE-FILE-011` Downloads of private files MUST NOT use permanent public URLs; presigned URLs live
  at most 5 minutes.
- `BE-FILE-012` **Derivation pipeline.** For files attached to records whose search declaration
  makes attachments searchable ([BE-SRCH-024](210-search.md)), jobs MUST, after the file is clean:
  detect the type by content; extract the text layer; run OCR on pages without a usable text layer;
  compute the page features used by the page check ([BE-SRCH-071](210-search.md)). The results are
  stored as derived objects next to the original: `<key>.txt` (text, page-delimited),
  `<key>.ocr.json` (OCR with confidence), `<key>.pages.json` (page features). Derived objects serve
  search and are never shown to users who cannot read the file.
- `BE-FILE-013` Derived objects MUST inherit the original's classification, permissions, storage
  class and retention, and MUST be deleted or anonymised together with the original (deletion,
  disposition, GDPR erasure). Page images needed for embedding SHOULD be rendered on demand from
  the original and not persisted; if cached, the cache follows the same rule and is short-lived.
- `BE-FILE-014` Extractors are pluggable components behind a core interface (type in, derived
  objects out); type detection and Office/email extraction use Apache Tika, PDF layout and OCR use
  the tools chosen in open decision 14
  ([90-appendices/open-decisions](../90-appendices/open-decisions.md)).
- `BE-FILE-015` OCR MUST have a model for every language in the language registry
  ([10-frontend/106-typography](../10-frontend/106-typography.md)); adding a language to the
  registry adds its OCR model in the same change.

## Extension points

- `BE-FILE-020` Deployments MAY add storage classes and bucket mappings as configuration.
- `BE-FILE-022` Apps MAY add extractors for their formats (e.g. CAD) through the BE-FILE-014
  interface; their output follows BE-FILE-012 and BE-FILE-013.
- `BE-FILE-021` Apps MAY add preview generators for their formats (e.g. CAD viewers) as jobs.
