# 501 · Continuous integration

## Principle

**Pipeline logic lives in the repositories as `just` recipes running inside the CI container
image.** The CI system (GitHub Actions) only triggers recipes. Every recipe runs identically on a
developer machine, in CI, or on another CI system.

## Standard recipes (every repository)

| Recipe | Does |
|---|---|
| `just setup` | Install toolchain dependencies from lockfiles |
| `just fmt` | Format (Ruff format, Prettier) |
| `just lint` | Ruff (incl. `S` rules), import-linter, ESLint, Stylelint, markdownlint, hadolint, shellcheck |
| `just typecheck` | mypy, vue-tsc |
| `just generate` | Run all generators |
| `just check-generated` | `just generate` then `git diff --exit-code` |
| `just sync-config` | Copy the shared tool configuration from the pinned `platform` commit ([DEL-TOOL-003](504-toolchain.md)) |
| `just check-config` | Fail if the shared configuration differs from the pinned `platform` commit |
| `just test-unit` | Vitest unit, integration and contract tests |
| `just test-backend site=minimal\|full` | Frappe tests on the given site profile |
| `just test-e2e` | Playwright against the disposable stack |
| `just api-diff` | Schema and error-catalog diff against the last release tag |
| `just scan` | gitleaks, Trivy (filesystem, licences) |
| `just ci` | The level-1 sequence below |

`platform` adds: `just build-image`, `just sbom`, `just scan-image`, `just sign`,
`just test-platform`, `just release`, `just deploy env=staging|production`.

## Level 1: app pull requests (every app repository)

1. `just setup` — checkout the app plus core and its `required_apps` at the versions in
   `platform.lock` (or at branches named in the PR description for cross-repository changes).
   A required app not yet in `platform.lock` (not yet conforming, FND-CONF-005) is checked out at
   its `main`.
2. `just lint`, `just check-config` and `just typecheck` (frontend checks run with core's
   toolchain over the app's `frontend/`).
3. `just check-generated`.
4. `just api-diff`.
5. `just test-unit`.
6. `just test-backend site=minimal`.
7. `just scan`.

## Level 2: platform (on every change to `platform.lock`, and nightly)

1. Pushing a release tag `vX.Y.Z` ([502-releases](502-releases.md)) in an app repository makes
   Renovate, on its next scheduled run, open a pull request in `platform` that bumps that app in
   `platform.lock` to the tag and the commit it points to. Renovate follows tags, not branches:
   a merge to `main` without a tag never reaches `platform.lock`, and pre-release tags
   (`vX.Y.Z-rc.N`) are not proposed.
2. `just build-image` — the full image with all apps and the built frontend.
3. `just test-platform` — cross-app contracts ([40-testing/403-contract-tests](../40-testing/403-contract-tests.md)).
4. `just test-backend site=full`.
5. `just test-e2e` — on the built image, desktop and mobile.
6. `just sbom`, `just scan-image` — fail on fixable critical/high vulnerabilities.
7. On `main` only: `just sign` and push to the registry with the platform version tag.

## Cross-repository changes

A change that needs two or more repositories at once (for example a feature app that uses a new
core sdk function) cannot wait for Renovate: neither half passes level 2 alone. `platform.lock`
holds only tags, so the combination is tested with pre-release tags:

1. Open one pull request per repository. Level 1 checks each against the branches named in its
   PR description.
2. On the head commit of each PR branch, push a pre-release tag (`vX.Y.Z-rc.N`, the version the
   repository will release). Pre-release tags are ignored by Renovate.
3. Open a `platform` pull request that sets those apps to their pre-release tags and commits by
   hand. Level 2 runs on that combination. New commits on a PR branch need a new `rc.N` and an
   update of the `platform` pull request.
4. When level 2 is green, merge in order `<core-app>` → apps, and tag each merged `main` with
   the release tag `vX.Y.Z`.
5. Set the `platform` pull request to the release tags (close any Renovate pull request for the
   same tags), let level 2 pass again, and merge it. `platform.lock` on `main` never keeps a
   pre-release tag.

## Rules

- `DEL-CI-001` Every step listed above is mandatory; a repository MUST NOT disable a step without an
  ADR.
- `DEL-CI-002` CI trigger files MUST only call `just` recipes; no pipeline logic in CI YAML.
  App repositories' trigger files call the reusable app-CI workflow of the `platform` repository,
  pinned to a commit SHA; that workflow runs `just ci` in the CI image, with MariaDB and Redis as
  job services.
- `DEL-CI-003` CI MUST run in the pinned CI container image built from the `platform` repository.
- `DEL-CI-004` CI runners MUST run on infrastructure separate from production. GitHub-hosted
  runners meet this; a self-hosted runner, if ever added, MUST NOT run on a production host.
- `DEL-CI-005` A red `main` in any repository MUST be fixed before other merges in that repository.
- `DEL-CI-006` CI logs MUST NOT print secrets; secrets are injected as environment variables from
  SOPS-decrypted files or GitHub Actions secrets (environment secrets where possible), scoped to
  the jobs that need them.
- `DEL-CI-007` CI trigger files MAY use actions only for plumbing (checkout, cache, registry
  login); the job runs in the CI image via `container:`. Every action not published by GitHub
  itself MUST be pinned to a full commit SHA.
