# 503 · Continuous delivery

## Target

A VPS running Docker Compose. Production and staging are separate compose projects (staging on its
own host when resources allow).

## Image

One immutable image per platform release (bench, Frappe and all apps at the locked versions,
built frontend), built only in CI from the `platform` repository.

## Deploy procedure (`just deploy env=… version=…`)

1. Manual approval (GitHub environment `staging` / `production` with required reviewers).
2. Verify the image signature (cosign).
3. Encrypted backup of the database and a snapshot of the object store
   ([60-operations/601-backup-and-restore](../60-operations/601-backup-and-restore.md)), and record
   the rollback point (`DEL-CD-007`).
4. Pull the image from the GitHub Container Registry on the target host.
5. Run `bench migrate` in a one-off container from the new image.
6. Replace web, workers, scheduler and socket.io containers, with the compose file of the
   released version.
7. Smoke test: health checks plus login and one journey per app.
8. Record an Audit Event "deployed `<version>` by `<user>`".

## Rollback procedure (`just rollback env=…`)

Started by hand (workflow *CD · Platform · Rollback*) when a deploy fails after its backup, or when
a deployed version turns out bad. It needs the same approval as a deploy and never runs at the
same time as one.

1. Manual approval (same GitHub environment as the deploy).
2. Read the rollback point the last deploy recorded; verify the previous version's image
   signature.
3. Stop every container that runs the platform image, so nothing writes during the restore.
4. Restore the pre-deploy backup: database and object store together (`OPS-BAK-001`).
5. Start the previous version with its own compose file; clear the cache. No migration: the
   restored database is the one that version ran on.
6. Smoke test.
7. Record an Audit Event "deployed `<previous version>` by `<user>`".

Data written between the backup and the rollback is lost, including the audit events of that
period. After a first deploy there is no previous version: restore by hand if needed.

## Deploy host

Each environment lives in its own directory on its host (`/srv/platform/<env>/`) with the encrypted
environment file (`DEL-CD-005`). The two host scripts live in the `platform` repository
(`deploy/host/`); each deploy copies the released version's scripts to the host before its backup,
so a rollback restores with the script that made the backup:

| Script | Contract |
|---|---|
| `backup.sh` | Encrypted, consistent backup of the database and the object store (`OPS-BAK-001`, `OPS-BAK-003`); prints the backup ID on its last line |
| `restore.sh <ID>` | Restores that backup, database and object store together |

The deploy keeps two state files next to them: `current-version` (the version whose smoke test
passed last) and `rollback.env` (the rollback point: previous version, backup ID, version being
deployed).

## Rules

- `DEL-CD-001` Images MUST NOT be built on servers; servers only pull signed images from the
  registry.
- `DEL-CD-002` Every release MUST be deployed to staging and pass the smoke test before production.
- `DEL-CD-003` Steps 2, 3 and 8 are mandatory and MUST NOT be skipped, including for hotfixes.
- `DEL-CD-004` Rollback = previous image + restore of the pre-deploy backup (patches are not
  reversible), by the rollback procedure above. The rollback procedure MUST be tested at least
  quarterly on staging.
- `DEL-CD-005` Secrets are provided to containers from the host's encrypted environment files, never
  baked into images.
- `DEL-CD-006` Staging doubles as the integration sandbox; it MUST contain only synthetic data.
- `DEL-CD-007` A deploy MUST NOT change anything on the host unless it can be rolled back: both host
  scripts exist, and the rollback point (previous version and backup ID) is recorded right after
  the backup. A deploy MUST NOT start while the last deploy to the same environment neither
  finished nor was rolled back.
